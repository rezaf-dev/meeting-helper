# Implementation notes

MeetingHelper is a native macOS 26+ SwiftUI application. It uses the Speech framework's `SpeechTranscriber` and `SpeechAnalyzer`; it does not use Siri/cloud dictation or send audio to an API. Initial language model assets are downloaded through Apple's `AssetInventory`.

## Data path

1. AVAudioEngine captures the default microphone. A private Core Audio process tap captures mixed system output, excluding this app by bundle ID. A private aggregate device feeds its input buffers to the system speech pipeline. Playback remains unmuted. No windows or displays are enumerated and no display capture is requested. NSAudioCaptureUsageDescription describes the separate system-audio permission. Startup failures destroy the IO procedure, aggregate device, and tap in reverse order. Denied audio permission may yield silence rather than an error; the settings screen explains how to grant access without inferring denial from ordinary silence.
2. Each source owns an independent speech pipeline. Captured samples are copied before the capture callback returns, handed to a bounded 32-frame stream, and resampled by a converter confined to a background task. A second bounded stream feeds the analyzer. Overflow is counted and shown; memory cannot grow through unbounded audio buffering.
3. Provisional hypotheses replace one another. Final results replace provisional ranges and are retained separately. Microphone and system inputs are source labels; the app does not identify individual remote speakers or perform acoustic echo cancellation. Headphones avoid system playback entering the microphone.
4. The transcript retains at most 500 finalized segments. The main view renders the latest 180; the floating view shows three. The saved chat merges finalized segments into a separate persistent archive. Export uses that archive, including finalized captions beyond the live retention limit and earlier capture runs in the same chat.
5. When the user enables cloud assistance, only text goes to `https://openrouter.ai/api/v1/chat/completions`: up to 12,000 characters of recent finalized transcript, 4,000 characters of notes, 4,000 characters of prior recap, 3,000 characters of live intent, and 2,000 characters of reply draft. OpenRouter routes text to the selected model provider; both parties' data policies apply. No direct OpenAI request path remains.
6. The default configurable model is `google/gemini-3.1-flash-lite`. Requests use OpenRouter's Chat Completions format, `provider.sort: latency`, and `reasoning.enabled: false` (honored where supported). The model browser loads the public catalog and filters for text input/output. No audio model endpoint exists in the app. SSE role/reasoning/usage frames are ignored, content deltas are displayed, and `[DONE]` confirms completion. Credit errors, mid-stream provider failures, and output truncation are reported. A request UUID prevents canceled requests from writing into newer answers.
7. Automatic help debounces changed provisional and final captions for 1.2 seconds, with a minimum two-second start interval and one in-flight request. New speech cancels a pending automatic answer. Handled caption IDs/text prevent repeated analysis; acknowledgment-only changes and turns ending with the microphone are consumed without a request. New transcript text and previous advice are separate prompt fields. Automatic output is buffered until successful completion, suppressing NO_UPDATE, legacy no-clarification messages, and exact duplicate answers. The quiet window estimates a pause from recognition updates, rather than audio-level VAD. Continuous speech defers automatic help; manual actions remain available. Manual requests preempt automatic work and reserve 12 seconds before automatic help can replace the answer. An automatic request error pauses automatic help until the user retries or re-enables it. Errors are visible; no model fallback occurs silently. Explicit Catch me up results become the compact prior recap. Without a recap, context beyond the recent transcript window is omitted.
8. The always-visible live intent pad is separate from the transcript and background notes. Edits invalidate an in-flight request, increment an intent revision, and debounce a new reply for 900 ms when cloud sharing and live-note updates are enabled. Caption-triggered requests wait while an intent update is pending. New guidance is snapshotted into each request, and successful replies record the applied revision. Apply note bypasses the debounce. Empty transcripts are allowed for intent-directed reply preparation. Live notes are saved with the chat, never used as recognition vocabulary or spoken transcript content.
9. An optional saved profile persists in UserDefaults (`profile.note`, `profile.include`). The request builder caps it at 2,000 characters and inserts it as a separate stable message before changing meeting text. The current live intent overrides conflicting profile preferences. Disabling profile inclusion passes an empty string and sends no profile message. Profile changes cancel outdated requests but do not create additional calls. A random `session_id` derived from the current capture UUID supports provider stickiness; there is no assertion that a cache hit occurs.

## Session lifecycle

Start creates a new in-memory timeline. Source and locale controls are locked during capture. Each selected source starts independently; a failed source is canceled and shown as a warning while any successfully started source continues. The status names the active inputs. If neither starts, all capture resources are released and a fatal error is shown. Stop ends capture and finalizes local recognition. Clear removes retained transcript, notes, live intent, reply draft, and AI context. Quit releases capture resources; finalized chat data is autosaved locally. Audio is not recorded to disk. Settings and vocabulary persist in UserDefaults. Finalized captions, notes, intent, drafts, and AI answers with request context persist as unencrypted JSON in Application Support/MeetingHelper/Chats; the latest chat is restored at launch. New chat saves the current chat before resetting. Deleting a chat removes its file, while exported copies remain separate. OpenRouter credentials persist unencrypted under the provider-specific openrouter.apiKey preference. A one-time migration tries to read the previous OpenRouter Keychain item with authentication UI disabled and removes it on successful import. Failed access requires re-entry; it never prompts or blocks local save. Legacy deletion is best effort. Saving or deleting marks migration complete so a removed key cannot be restored from Keychain. Direct-OpenAI credentials and sharing settings are not migrated.

The saved profile is a durable preference and is not cleared with a meeting. Its text is shared through OpenRouter only when both profile inclusion and cloud text sharing are enabled.

The application delegate sets a regular activation policy and explicitly assigns `NSApplication.applicationIconImage` from the bundled ICNS, then redraws the Dock tile. This supplements `CFBundleIconFile` and addresses stale generic icons in locally rebuilt bundles without deleting system icon caches or changing Dock pins.

## Floating panel and capture limitations

`FloatingCaptionController` owns a nonactivating `NSPanel` hosting the existing SwiftUI caption view. It sets `.floating` level, `.canJoinAllSpaces`, `.canJoinAllApplications`, `.fullScreenAuxiliary`, `.stationary`, and `.ignoresCycle`. It disables hiding on deactivation and restores/saves its frame. This replaces the old SwiftUI Window attachment callback, which could run before `view.window` existed and never apply the window policy. The panel shows with `orderFrontRegardless` and does not activate the app when displayed from the menu bar. Close, Hide, and the app/menu commands update a shared visibility state.

`FloatingPanelPolicy` applies the optional `.sharingType = .none` hint. The flag is a legacy compatibility request, not a privacy guarantee; Apple's current documentation explicitly advises against relying on it for capture omission. It does not change another application's ScreenCaptureKit filter. Actual Zoom/Teams/Meet full-display behavior has not been verified and can vary. The app labels this limitation, offers a quick Hide action, and recommends sharing a specific app window or using an unshared display. It does not automatically detect screen-sharing sessions or claim to be invisible.

## Performance and verification

App CPU and footprint readings exclude Apple's external speech service. Use Activity Monitor to measure the complete workload, including the meeting app, WindowServer, and speech services. Caption delay is an approximation based on the audio timeline, and loses precision after dropped buffers. AI first-text latency is measured from the outgoing request; it excludes time waiting for finalized captions and the automatic throttle interval. It is not total spoken-question-to-answer latency.

Test under the actual meeting workload: remote audio + microphone + screen sharing + normal browser tabs. Check captions, loss/duplication, uncertain words, dates/numbers, headphone changes, capture permissions, stop/restart, network failure, rate limits, and an hour-long session. Local and cloud performance claims remain unverified until these are measured on representative audio.

## Visual direction

Native system surfaces with a restrained blue accent (#2459D4), dark slate text (#253548), cool secondary surfaces (#F5F7FA), soft separators (#DCE3ED), and green reserved for active capture. SF system typography; 23 pt default captions and 11–15 pt controls. The transcript is the dominant left pane, with a narrow right pane for short language help. Source markers encode origin rather than speaker identity. The floating window provides large text across workspaces.

## Scope

This first version uses Apple recognition. FluidAudio comparison, per-app audio selection, remote-speaker diarization, translation, and Developer ID distribution/notarization are follow-up work. No numeric latency, accuracy, memory, or battery guarantee is asserted.

## Answer pane and scrolling

The answer pane has a 440-point minimum width with no maximum cap; the transcript can shrink to 360 points. The split divider remains draggable. A compact header, one-row AI actions, and a shorter live-note editor leave more vertical room for the answer. Hide note removes the editor and context disclosure from the layout without changing their model data or AI request behavior.

FollowingScrollView tracks proximity to the bottom (32-point tolerance) during manual scrolling. Content growth while idle never changes that reading preference. When following, text revisions and content-height changes scroll to a bottom sentinel without per-token animation. During a scroll gesture, updates do not force scrolling. Returning to the bottom resumes following; Latest answer explicitly restores it. A local-only MeetingUIProbe fixture uses the real UI with synthetic paragraphs and append/replace/stream controls under a separate bundle identifier, without starting capture or AI requests.

## English help preferences

AIHelpPreferences is snapshotted into each AIClient request and encoded as system instructions with action-specific word and token budgets. Settings persist ai.englishLevel (default intermediate), ai.answerLength (default brief), and ai.importantOnly (default true). These explicit settings take precedence over conflicting free-text saved profile preferences and apply independently of profile inclusion. Live intent continues to direct the reply within the chosen word budget. Changing a help setting cancels an outdated request; it does not make a new request by itself.

Brief help asks for one usable answer in one or two sentences, without headings or repeated transcript: 35 words for live/question/reply, 45 for explanation, 80 for recap. Balanced permits 80/100/160; Detailed permits 100/180/240 respectively. Token limits leave headroom instead of cutting a sentence at the requested word count. Essential uncertainty and the safeguards against invented facts or commitments remain in every mode. Important-only filtering never suppresses an explicitly requested reply, question, or recap. Model compliance and real output length still need live evaluation; automated checks verify prompt construction and budgets, not model quality.
